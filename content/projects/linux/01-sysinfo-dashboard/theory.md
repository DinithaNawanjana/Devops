# Deep Dive: System Information Dashboards

## Why this matters
Before any monitoring stack exists, the first tool an engineer reaches for is a
shell script that answers "what is this box doing right now?". Understanding
*where the kernel exposes state* is what separates copy-paste admins from people
who can debug a server with nothing but Bash.

## Where the data actually lives
Linux exposes almost everything through **virtual filesystems** — files that
aren't on disk but are generated by the kernel on read:

| Source | Holds |
|--------|-------|
| `/proc/cpuinfo` | per-core CPU model, flags |
| `/proc/loadavg` | 1/5/15-min load averages + running procs |
| `/proc/meminfo` | every memory counter the kernel tracks |
| `/proc/uptime` | seconds since boot |
| `/sys/class/...` | devices, thermal zones, network counters |

Tools like `free`, `uptime`, `nproc`, and `df` are mostly *formatters* over
these files. Reading the raw file (`cat /proc/loadavg`) and parsing it yourself
is often more portable than depending on a tool's output columns.

## Techniques you'll practise
- **Command substitution** `cores=$(nproc)` to capture output into variables.
- **`awk` field extraction** to pull one column out of `free`/`df` — e.g.
  `free -m | awk '/Mem:/ {print $2}'`.
- **`printf`** for aligned, predictable output (never trust `echo` for
  formatting across shells).
- A **`--help`/usage guard** so the script behaves like a real CLI tool.

## Common pitfalls
- Parsing `df` without `-P` (POSIX) — long device names wrap onto two lines and
  break your `awk` column math. Always use `df -P`.
- Assuming `free` exists — on minimal/busybox systems it may not; reading
  `/proc/meminfo` is the robust fallback.
- Locale-dependent number formats; force `LC_ALL=C` for stable parsing.

## Real-world
This is the seed of every "node health" check, the body of a Nagios/Prometheus
textfile-collector script, and the first thing you SSH in and run during an
incident.
